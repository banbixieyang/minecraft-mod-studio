# 拆解别人的 mod

> **证据等级 `verified-26.3`**：本文的每一步都在本机跑通。
> 「改数值 → 真回写生效」这条链路用两个真实 mod（Goety 基础库、Goety Delight）
> 验证过，生成的 TOML 与 Java 覆写代码都真编译通过。

做模组最难的不是写代码，是**想清楚要做什么**。
拆解别人的 mod 就是反过来 —— 先看清别人做了什么，再决定自己要不要。

---

## 1. 为什么这事值得做

一个成熟 mod 里有大量「踩过坑才写出来」的东西：
数值平衡的取值、事件的挂法、配方设计的思路。
这些光看代码很难看懂，**但拆开成条目就一目了然**。

这个工具能做到：

| 你想要的 | 拆解台能给你 |
|---|---|
| 这个魔法到底多贵 | 灵魂消耗 / 吟唱时长 / 冷却，全是可直接改的字段 |
| 这件装备加多少攻击 | 装备材质条目（附魔值、防御值、耐久） |
| 有哪些可调数值 | 数值配置分组，带默认值、取值范围、说明、所属配置文件 |
| 它挂了哪些事件 | 代码能力分组，每条带证据说明凭什么这么判断 |
| 这个 mod 怎么玩 | 配方、掉落、进度，全部逐条列出 |

## 2. 四步走

```
导入 → 分析 → 拆解台研究 → 导出成新包
```

### 2.1 导入

顶栏「分析」→ 把 jar 拖进去。

分析器做三件事：

| 看什么 | 怎么看的 | 准不准 |
|---|---|---|
| 物品、方块、配方、掉落、矿物生成、进度 | 读 jar 里的 JSON 资源 | **准** —— 那就是数据本身 |
| 状态效果、法术、附魔、可调数值 | 读 class 字节码的常量池 | 有证据支持，带证据列出 |
| 加载器、版本、modId | 读 mod 描述文件 | **准** |

支持的加载器：Fabric、Quilt、Forge、NeoForge、老 Forge（mcmod.info）。
描述文件不在标准位置（被二次打包过）也能认出来。

### 2.2 打开拆解台

「分析」面板里找到刚导入的 mod → 点「拆解」。

### 2.3 研究

左侧是分组，右边是条目列表，中间是表单。

**每条内容都带一个「速览」**，告诉你这条是什么：

- 数值配置：`config/goety-spells.toml ▸ Spells.Vexing Spell` + `范围 0 ~ 2147483647` + 说明
- 状态效果：注册表 id + 中文名 + 属性修饰符
- 配方：类型 + 材料 + 产物

**分页**：条目多的分组（数值配置动辄上千条）每页只渲染 200 条。
**用搜索框过滤**才能定位到具体条目 —— 这是正常用法，不是卡了。

### 2.4 导出

改完数值 → 「预览生效产物」→ 看清楚要生成什么 → 导出成新包。

包会进 `~/.mcstudio/packs/`，之后一键装到任意工程。

## 3. 关键：改数值怎么才真生效

这一节是本文的核心，也是这个工具和「只能看」的分析器最大的区别。

### 3.1 两条覆写路径

| 路径 | 文件 | 生效时机 | 适合 |
|---|---|---|---|
| **配置覆写** | `config/<mod>/xxx.toml` | 游戏启动时读配置 | 数值在 Forge 配置系统里的 mod |
| **运行时覆写** | `src/main/java/.../XxxConfigOverrides.java` | 进游戏立刻生效 | 同上，但不想重启游戏 |

两条**同时生成**，你可以按场景挑。

### 3.2 为什么要两条都要

TOML 覆写是「官方姿势」，但改完要重启游戏才能看到效果。
Java 覆写直接改内存里的值，进游戏就是新的 —— 调试数值时省时间。

### 3.3 生成的说明文档

导出包里还有一份 README，写清楚**改了什么、原本是多少**。
以后回头看这个包，知道它为什么长这样。

### 3.4 ⚠️ 不是所有 mod 都能这么改

| 数值写在哪 | 能不能改 | 为什么 |
|---|---|---|
| Forge 配置系统（ForgeConfigSpec） | ✅ 能 | 有配置文件可以覆写 |
| 代码里的常量 | ❌ 不能 | 要改源码重新编译，性质完全不同 |
| 数据驱动的 JSON（26.x 的附魔） | ⚠️ 改 JSON | 覆写资源文件，不是配置覆写 |

引擎会明确告诉你哪种情况：
数值配置分组里能改的都有 `tomlPath`（真实配置路径）和 `configFile`（所属文件）。

## 4. 拆解时能看到什么

### 4.1 资源还原（准）

直接从 JSON 读的，**几乎 100% 准确**：

- 物品、方块（含工具/盔甲类型推断）
- 配方（有合成、熔炼、锻造、烧制、切石等类型）
- 战利品表（掉落什么、多少）
- 矿物生成（哪个维度、什么高度、多少个）
- 进度（标题、说明、图标、框架）

### 4.2 字节码还原（有证据）

从 class 常量池读的。每条都带「证据」，你可以自己判断可不可信。

**能读出来的**：
- 注册 id（`register("xxx")` 的字符串参数）
- 数值常量（方法里出现的数字）
- 最大等级（无参 + 返回整数 + 值在 1~99）
- 父类（判断「这是不是一个 MobEffect 子类」）
- 调用了哪些 API（常量池里的类引用）

**读不出来的**：
- 方法体逻辑（除非值在 return 之前）
- 混淆过的方法名（发布包常见）

### 4.3 看原作者的代码（真反编译）

常量池只能证明「它引用了哪些 API」，**看不到方法体**。想知道一个道具的效果到底怎么写的，
就用分析面板顶栏的 **「反编译看源码」**：

1. 先导入 / 选中一个 jar（发布版只有 `.class`，没有 `.java`，这一步是必须的）
2. 点「反编译看源码」，等它跑完（大包几分钟，结果按 jar 缓存，第二次秒开）
3. 左边搜类名或包名，右边读源码；下面两行标签是**引用关系**

界面长这样：

- **左边**：这个 jar 里的全部类，按「类名 + 包名」列出来，可以在上面搜
- **右边**：反编译出来的真 Java 源码（带方法体、if/for、常量、注释位置）
- **底部「用到了」**：它引用了谁 —— 点击包内的类会直接跳过去，顺着这条线就能从
  「物品注册」一路追到「命中时干了什么」
- **底部「被谁用」**：谁引用了它 —— 想知道「这个工具类在哪被调用」就靠这个
- **「引用 N」按钮**：收起引用列表，把高度全给源码

反编译用的是 **ForgeFlower**（ForgeGradle 本来就会下载它，不额外装东西）。
找不到时按钮会明确告诉你放哪：

```
把 forgeflower*.jar 放到 tools/forgeflower.jar
或设置环境变量 MCSTUDIO_DECOMPILER 指向任意 fernflower/forgeflower jar
```

缓存放在 `~/.mcstudio/decompile/<jar 指纹>/`，**不会**往被分析 mod 的 `build/libs` 里丢东西。

> 参数名可能是 `var0`/`var1`：很多发布包编译时没带局部变量表，反编译器只能拿编号顶上。
> 这不是拆错了，是原件就没存名字。

### 4.4 能力识别

「代码能力」分组列出这个 mod 干了哪些事：

| 分类 | 例子 |
|---|---|
| 战斗 | 攻击命中回调、伤害拦截、死亡回调、掉落修改 |
| 属性 | 属性加成、状态效果、施加效果、回血 |
| 移动 | 允许飞行、重力控制、传送、移速、摔落保护 |
| 物品 | 食物、说明文字、数据组件、附魔、耐久 |
| 方块 | 方块实体、定时逻辑、破坏/交互回调 |
| 世界 | 生物群系注入、世界生成、战利品修改、结构生成 |
| 界面 | 自定义界面、HUD、创造栏、自定义渲染 |
| 技术 | 数据附件、存档数据、网络通信、定时任务、Mixin |

**Fabric 和 Forge 两套都认。** Forge mod 用的是 `AttackEntityEvent`、
`LivingDeathEvent` 这类事件名，和 Fabric 的 `AttackEntityCallback`
完全是两套命名，规则表两边都覆盖。

### 4.5 扩展提供的内容

某些 mod 的效果不在通用资源里，需要专门的扩展才能拆。
装上扩展后，拆解台会**多出分组**：

| 扩展 | 多出来的分组 |
|---|---|
| `goety-base` | 状态效果、法术、数值配置、酿造效果、附魔 |
| `goety-revelation` | 聚晶、套装词条、仪式配方 |
| `goety-delight` | 数值配置、状态效果、附魔、仪式/料理配方 |

> ⚠️ **改了扩展要重启服务。** 扩展是启动时一次性装载的
> （刻意对齐 MC 的 mod 语义）。忘了重启就会看到「分组没出来」。

## 5. 边界：拆不出来的东西

诚实说明比事后发现强。

| 情况 | 结果 | 为什么 |
|---|---|---|
| 发布包经过重映射 | 能认注册 id 和 API 用法；反编译后能看到逻辑，但方法名是 `m_12345_` 这类 | SRG/intermediary 名不可读 |
| 数值写在代码常量里 | 自动覆写拆不出来，但**反编译后能直接看到那个数字在哪一行** | 没有配置文件可覆写 |
| 纯代码 mod（无 assets/data） | 资源分组全空 | 本来就没资源 |
| 内嵌 jar 里的内容 | 单独列出来，可单独拆 | 外层只是个壳 |
| 混淆过的方法体 | 反编译能看到**逻辑结构**，可读性取决于混淆强度 | 名字被抹掉了，控制流还在 |

**发布包的判断依据**：jar 里有签名文件（`META-INF/*.SF`）就是发布版，
class 名一般是 SRG/intermediary。

## 6. 实战：一个完整例子

以 Goety Delight 为例（1.20.1 Forge 附属包）：

**第一步，导入并分析。** 识别出 163 物品、38 方块、46 核心配方、
111 条自定义配方、18 状态效果、5 附魔、33 条数值配置。

**第二步，找目标数值。** 「数值配置」分组搜 `cakeEffectRadius` ——
皇家蛋糕的效果半径，默认 32，在 `config/goetydelight-common.toml` 的
`[General]` 段里，取值范围 1~256。

**第三步，改值。** 改成 48。

**第四步，看生效产物。** 「预览生效产物」显示要生成 3 个文件：

```
config/goetydelight-common.toml     ← 配置覆写
src/main/java/.../GoetyDelightConfigOverrides.java   ← 运行时覆写
goetydelight-config-overrides/README.md              ← 改了什么
```

toml 里 `cakeEffectRadius = 48` 已经写进去了。

**第五步，导出成包，装进自己的工程。**

## 7. 排查清单

拆解结果跟预期不符时，按这个顺序看：

1. **报告里的警告列表** —— 引擎只说自己确定的事，不确定的地方一定在警告里
2. **分组的条目数** —— 为 0 说明这类内容在这个 mod 里确实没有
3. **mod 描述文件** —— 加载器/版本认对了没
4. **扩展是否生效** —— 改了扩展要重启服务
5. **是不是发布包** —— 有签名文件的话方法名认不出来是正常的
