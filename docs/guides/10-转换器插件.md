# 10 · 功能转换器插件

> 一句话：它**尽量**帮你搬，但绝不说「已经搬好了」这种谎。
> 能证实的自动改，不能证实的原样保留并写 `// TODO(转换)`，还告诉你该怎么改。

## 1. 它解决什么问题

同一件事在两个目标里写法经常不一样：

| 功能 | Fabric 26.3 | Forge 1.20.1 |
|---|---|---|
| 给玩家发消息 | `player.sendSystemMessage(..., bool)` | `player.displayClientMessage(..., bool)` |
| 解析资源 id | `Identifier.parse(...)` | `ResourceLocation.parse(...)` |
| 注册表按 id 取值 | `BuiltInRegistries.ITEM.getValue(...)` | `BuiltInRegistries.ITEM.get(...)` |
| 取游戏模式 | `player.gameMode()` | `player.gameMode.getGameModeForPlayer()` |
| 实体受伤回调 | `ServerLivingEntityEvents.AFTER_DAMAGE` | `LivingDamageEvent` + 事件总线 |
| 资源目录 | `data/ns/recipe/`、`items/` | `data/ns/recipes/`、`models/item/` |

前四行是**等价改写**，转换器敢自动改。第五行连回调签名都不一样，
硬替换只会得到「看起来对、一编译就炸」的代码 —— 转换器会明确标成「需人工」。

## 2. 三种用法

界面：顶栏 **「转换」** → 选来源（当前工程 / 贴一段 Java / 内置效果 / 分享包文件）、
选源目标与要转到的目标 → **预览转换** → 看报告 → **应用到当前工程** → 再点「生成」。
预览只读，应用要二次确认。

命令行（接 CI / 脚本）：

```bash
node studio.mjs convert help
node studio.mjs convert rules                     # 规则清单 + 加载诊断
node studio.mjs convert matrix                    # 目标之间有多少「有证据」的映射
node studio.mjs convert inspect projects/mymod     # 看抽出来的功能 IR
node studio.mjs convert run projects/mymod --to forge-1.20.1 --out /tmp/Converted.java
node studio.mjs convert apply projects/mymod --to forge-1.20.1 --yes --generate
node studio.mjs convert run my.mcpkg.json --to fabric-26.3 --json   # 结构化结果
```

`--json` 输出完整报告（含 `items` / `summary` / `patch`），退出码可直接让流水线挂掉。
`apply` 不给 `--yes` 一律拒绝。

HTTP（给别的工具接）：`GET convert/rules`、`GET convert/matrix`、
`POST convert/inspect`、`POST convert/preview`、`POST convert/apply`（须 `confirmed: true`）。
预览类接口绝不写盘。

## 3. 四档状态，别只看「自动率」

| 状态 | 含义 | 依据 |
|---|---|---|
| `ported` 自动完成 | 整段等价改写 | 积木库里同一个 op 的两份 Java 模板都经 Gradle 真编译过 |
| `adapted` 已改写 | 已自动改，建议编译确认 | 类名 / 方法名一一对应、参数形状相同；资源方言取自生成器 |
| `manual` 需人工 | 原样保留 + `// TODO(转换)` + 做法提示 | 加载器事件、注册入口、本地 jar 依赖 |
| `blocked` 做不到 | 目标没有对应实现 | 例如某条积木在目标下没有模板 |

报告里每一项都带 `rule`（哪条规则做的）、`notes`（依据）、`before/after`（改了什么）
和 `suggestion`（下一步）。`summary.autoRate` 只算 `ported + adapted`，
所以「自动率 100%」不代表整个功能真能跑 —— 一定要看「需复核」数量。

## 4. 中间表示：转换器只认一种形状

不管来源是工程、分享包、一段 Java、内置效果还是积木库，先抽成 `mcstudio.feature` IR：

```json
{
  "format": "mcstudio.feature",
  "version": 1,
  "id": "attack_lifesteal",
  "name": "攻击吸血",
  "kind": "effect",
  "origin": { "type": "effect", "targetId": "fabric-26.3" },
  "requires": { "platform": ["fabric"], "mcVersion": ["26.3"] },
  "content": {
    "entries": {},
    "java": [{ "name": "攻击吸血", "target": "init", "code": "..." }],
    "programs": [],
    "files": [],
    "deps": []
  }
}
```

抽平后每个部件有稳定 id（`java/0`、`entry/item/0`、`program/0`、`file/0`、`requires`），
规则按 id 回填，报告也按 id 对照。

**两个天生可移植的东西**：

- `content.entries`（内容条目）是平台无关的，生成器拿同一份数据按目标适配器重出 Java 和资源；
- `content.programs`（积木程序）也是平台无关的，编译器按目标挑模板。

所以转换器对它们只做检查（目标下有没有模板），不做改写。应用完**必须再点一次「生成」**，
让新目标把整套资源重出一遍。

## 5. 内置规则

| 规则 | 优先级 | 干什么 |
|---|---|---|
| `builtin.blocks` | 100 | 按积木库两份真编译过的模板整段改写 |
| `builtin.symbols` | 90 | 低风险符号替换（资源 id、注册表、发消息、游戏模式） |
| `builtin.events` | 70 | 识别加载器事件 / 注册 API，标 `manual` 并写 TODO |
| `builtin.resources` | 60 | 资源方言：复数/单数目录、战利品表键名、配方结果键名 |
| `builtin.entries` | 55 | 条目保持原样，重写 `requires`，修 26.x 的 worldgen 尺寸下限 |
| `builtin.programs` | 55 | 检查积木在目标下有没有实现，缺的标 `blocked` |
| `builtin.deps` | 40 | 本地 jar 是二进制，列出需要换的目标版本 |

优先级大的先跑；每条规则开始前都会刷新部件，所以后面的规则看得见前面改过的代码。
一条规则抛异常只跳过它并记进诊断，其它规则照常跑。

## 6. 写自己的规则（插件）

一个 `.mjs` 文件导出 `rule` 即可：

```js
export const rule = {
  id: 'example.myapi',
  label: '示例：自己的 API 换包名',
  priority: 50,
  from: { platform: 'fabric' },        // 省略 / '*' = 任意
  to:   { platform: 'forge' },
  match(ctx) { return true; },          // 可选
  convert(ctx) {
    // ctx = { from, to, feature, parts, targets }
    // parts = 抽平后的部件，含 id / kind / label / code / data / path
    return {
      changes: { 'java/0': { code: '...' } },   // 按 part id 精确回填
      items: [{
        id: 'java/0/myapi', kind: 'java', label: '自己的 API',
        status: 'adapted', confidence: 0.8,
        notes: ['依据 xxx'], suggestion: '编译确认',
      }],
      notes: [],
    };
  },
};
```

`changes` 支持 `code` / `data` / `path` / `todo`（追加 `// TODO(转换): ...`，不会覆盖别人的改写）。
**不要直接改 `draft`** —— 用 `changes` 回填，引擎才能记下「哪些部件被改过」。

放这三个位置之一，引擎启动时自动发现（后面的覆盖前面同 id 的规则）：

```
内置 core/convert/rules/           随引擎发版
~/.mcstudio/convert/               装一次，所有工程可用
<工程>/.studio/convert/            只对当前工程生效
MCSTUDIO_CONVERT=/path/to/dir      CI / 多版本切换
```

可照抄的样板：[examples/extend/convert/demo.mjs](../../examples/extend/convert/demo.mjs)，
它同时也是 `tests/convert.mjs` 的夹具。

### 加一个新版本怎么办

新目标先按《09 · 扩展与工具包》写适配器（`~/.mcstudio/targets/`），
然后给它补规则：把新版本与原版本的 API 差异写进 `SYMBOL_TABLE` 风格的规则里。
**只有两边确实等价的才自动改**；拿不准就返回 `manual` + 做法提示，
加载诊断会告诉你规则有没有正常装载（`node studio.mjs convert rules`）。

## 7. 应用到工程后改了什么

`apply` 只动 `.studio/project.json`：

- `target` 整体换成新目标的 `defaults`（含 `javaVersion`，不能只改 id，否则 build.gradle 会坏）；
- `hooks.java` 换/追加转换后的代码（源是外部代码时是追加，不清掉已有钩子）；
- `visual.programs`、`localDeps`、条目按来源回填；
- `state.convert` 记一笔溯源（从哪到哪、自动率、需复核数）。

资源文件不在这里塞，交给「生成」。生成完再「构建 jar」验证 ——
`manual` 项里的 TODO 就是编译前必须处理的清单。
