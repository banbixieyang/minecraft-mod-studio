# 复用与分析

这份文档讲两件配套的事：

- **效果库**：把做过的东西存起来，下次一键装进别的工程。
- **分析器**：拆开一个现成的 mod，看清它做了什么，把能用的部分留下来。

两者共用同一个数据单位 —— **包（Pack）**。理解包，剩下的都是它的操作。

---

## 一、包是什么

一个包就是一个 JSON 文件，扩展名 `.mcpkg.json`。里面可以装五类东西：

| 装什么 | 说明 |
|---|---|
| 内容条目 | 物品、方块、配方、矿物生成、进度…… 就是你在编辑器里填的那些 |
| Java 代码 | 插到钩子锚点里的片段（`@hook:init` 等） |
| JS 钩子 | 生成前跑的脚本 |
| 贴图 | 你自己画的 PNG（自动改色的不用带，会按新工程的配色重新生成） |
| 参数 | 让包可以调的东西，比如吸血比例 |

装内容就是「一套装备」，装代码就是「一个效果」，两样都装就是「混合包」。

之所以统一成一种文件，是为了让**手工攒的**、**分析出来的**、**别人给你的**东西长得一样。
否则「分析完能不能直接用」这个问题永远说不清。

## 二、效果库

顶栏点 **库** 进去。

### 三个来源

| 来源 | 位置 | 谁能改 |
|---|---|---|
| 内置 | 编辑器自带 | 只读 |
| 我的库 | `~/.mcstudio/packs/` | 可改，所有工程共享 |
| 本工程 | `<工程>/.studio/packs/` | 可改，跟着工程走 |

同名时「本工程」盖住「我的库」—— 某个工程要特调一版，不用另起名字，也不会污染别的工程。

### 攒一个包：从工程捕获

点右上 **从工程捕获**：

1. 选类型（物品 / 方块 / 配方……），勾要带的条目
2. 选「怎么带」
   - **带上被引用的内容**（默认）—— 你勾了红宝石剑，它会把剑引用的工具材质、材质引用的红宝石材料一起带走
   - **只带强依赖** —— 只带材质这类结构性引用
   - **只带我勾的** —— 你自己保证完整
3. 起名字，选存到哪

默认那条很重要。只勾剑不勾材质，装到别的工程里剑就是一把「材质找不到」的剑。
自动闭包就是为了避免这种半残的包。

### 装一个包

点包卡片看详情 → **装进当前工程** → 先看到「会发生什么」，确认后才真的装。

装之前那一步不是多余的，它会告诉你：

- 加入几项内容、几段代码、几张图
- **哪些 id 会撞名、会被改成什么**（`ruby_sword` → `ruby_sword_2`）
- 包里有没有引用「原工程里但没被带走」的东西（这会导致装完有缺失）

撞名不是直接跳过，而是改名，并且**把包内所有指向它的地方一起改**：
配方里的材料、掉落表里的物品、进度里的图标，全都跟着变成新 id。

### 参数

包可以带参数。代码或文本里写 `{{key}}`，安装时填什么就替换成什么。

比如「攻击吸血」包有两个参数：吸血比例、单次上限。装的时候填 `0.3`，生成出来的就是：

```java
float heal = damageTaken * 0.3F;
```

没定义、也没填的占位符会原样留在代码里，同时在安装报告里列出来 —— 不会静默吃掉。

## 三、分析器

顶栏点 **分析** 进去。

### 直接把别人的 jar 拖进来

顶栏点 **分析**，最上面就是一个拖放框：**把从网上下载的、别人发来的 mod jar 直接拖进去**
（或点「选择文件」），上传完自动开始分析。不用先知道它在服务端的绝对路径，
不用先解压，也不用把它挪到 `mods` 目录里。

上传走原始二进制（不做 base64 膨胀），上限 256 MB；文件副本落在 `~/.mcstudio/imports/`，
按内容哈希命名 —— 同一个包重复拖进来不会堆一地副本。
「管理已导入…」能列出、重新分析、删除副本，**只删副本，不碰你原来的文件**。
整个过程是只读解析，不会运行 jar 里的任何代码。

上传后服务端返回的是一个本地路径，因此「分析 → 勾选 → 打包 → 装进工程 → 存成笔记」
这一整条按路径工作的老链路一行没改就复用了。原来那三种入口也都还在：

- 手填路径（`.jar` / `.zip` / 解压后的目录 / 有 `build.gradle` 的源码工程）
- 「浏览文件…」翻服务端磁盘
- 「最近的 jar」扫本机构建产物、游戏 `mods` 目录、桌面 / 下载，以及刚导入的缓存

### 第三方发布包怎么认

自己构建出来的 jar 太规整了。别人发布的包可能是 Fabric、Quilt、Forge、NeoForge、
老版本的 `mcmod.info`，也可能压根没有 mod 描述文件（纯库 jar）。
分析器按格式逐个试，试不出来就用 `META-INF/MANIFEST.MF` 兜底，并**明确告诉你缺了什么**，
而不是悄悄给一份空报告。

`mods.toml` 这一类也按真实写法读：多个 `[[mods]]`、单引号、三引号多行描述、
跨行数组、注释里的 `#`、`${mod_id}` 占位符、`versionRange="[1.20.1,1.21)"` 里的 MC 版本。
ZIP 层单独处理了四种只在第三方包里见到的怪癖：自解压前缀导致的偏移错位、
没有 UTF-8 标志的 GBK 中文文件名、ZIP64 结束记录、流式打包留下的 data descriptor。

这些不是理论上的担心 —— `tests/import.mjs` 手工拼字节造了每一种样本逐一验证。

### 它到底在干什么

分三层，**每层的确定性完全不同**，界面上也分开显示：

**第一层：元数据 + 包特征** —— 从 `fabric.mod.json` / `quilt.mod.json` /
`mods.toml` / `neoforge.mods.toml` / `mcmod.info` 读。这是事实。

报告里有一节「这个包的特征」，说明**为什么只能看到这些**：
是否带签名（发布版）、是否被重映射成 intermediary / SRG 名、
jar 里有没有 `.java` 源码、有没有把别的 mod 打进 `META-INF/jars/` 或 `jarjar/`。
带内嵌 jar 的包，每个都能点「单独分析」拆出来走同一套界面 —— 整合包也能逐个看。

**第二层：内容** —— 从 jar 里的资源文件反推。也是事实，因为那本来就是数据文件本身：

| 从哪读 | 得到什么 |
|---|---|
| `assets/<ns>/models/item/*.json`、`assets/<ns>/items/*.json` | 有哪些物品（1.20.1 用前者，26.x 用后者） |
| `assets/<ns>/blockstates/*.json` | 有哪些方块 |
| `assets/<ns>/lang/*.json` | 中文名、英文名，以及只注册了没模型的物品（靠语言键发现） |
| `data/<ns>/recipe(s)/*.json` | 配方，能完整转成编辑器的配方条目 |
| `data/<ns>/loot_table(s)/**` | 方块挖掉掉什么 |
| `data/<ns>/worldgen/feature` + `placed_feature` | 矿物生成的尺寸、数量、稀有度、高度范围、维度 |
| `data/<ns>/enchantment/*.json` | **26.x 数据驱动附魔**：最高等级、每级经验代价、附魔效果 |
| `data/<ns>/mob_effect/*.json` | **26.x 数据驱动状态效果**：类别、作用属性 |

这条路比读代码可靠得多：类名和方法体可能被混淆，资源文件名不会。
而且读出来直接就是编辑器自己的条目格式，能一键导入。

#### 换任何一个 mod 都不会大面积踩坑

分析器要面对的不是「一个 mod」，而是「一堆来源不明的 mod」，所以下面这些是硬规矩：

**目录两套都认。** 1.20.1 的 Forge mod 用复数目录（`recipes/`、`loot_tables/`、
`models/item/`），26.x 用单数（`recipe/`、`loot_table/`、`items/`）。
引擎两个都列出来扫，读的时候按顺序试 —— 拿 1.20.1 的 mod 不会一片空白，
拿 26.x 的 mod 也不会因为目录名不同而漏。

**多命名空间归属判定。** 一个 jar 里常有好几个命名空间：主 mod 自己的、
依赖 mod 顺带打进去的、还有别的 mod 附带的资源。判定「算谁的」用两条规则：
命名空间等于 mod 描述文件声明的 modId，或者命名空间里有语言文件（作者认领过）。
`minecraft` / `forge` / `neoforge` / `fabric` 明确排除。

效果是：Goety Delight 的 jar 里带着 431 个 `assets/goety/` 的 patchouli 书，
不判归属的话整个清单会被书页糊掉；判完之后它的物品 / 方块数才是真实的 163 / 38。

**语言键里的假东西要滤掉。** mod 习惯用 `item.<modid>.<id>.info` / `.desc` / `.brew`
这类附属键写说明文字。这些不是物品。全量扫语言键会把它们变成 143 个「幽灵物品」，
清单直接虚高。带这些后缀的一律不算物品。

**进度标题要翻译。** 进度 JSON 里的标题常常是 `{"translate": "advancements.xxx.title"}`，
不查语言表的话界面上就是一串键名。引擎会把语言表一起查了再显示。

**内嵌 jar 要能拆开。** 整合包 / 附属包里常带 `META-INF/jars/` 或 `jarjar/` 的依赖。
引擎会把内嵌 jar 递归打开，能读出的都在报告里列出（modId、名称、加载器、文件数），
读不出的明确标「读不出来」，不假装成功。

**Forge 和 Fabric 的事件名是两套。** Fabric 写 `AttackEntityCallback`，
Forge 写 `AttackEntityEvent`；常量池里只会出现实际引用的那套。
能力识别规则表两套都写 —— 只写一套，Forge mod 的能力就会大面积漏判。

这些不是理论上的担心 —— `tests/generality.mjs` 用合成的 mod 逐一验证了这七类场景，
共 36 项断言。

**装备材质是推出来的。** 资源文件里没有防御值、挖掘速度、耐久这些数字 —— 它们在 class 常量里。
但「只认物品不管材质」会有个很难受的后果：盔甲生成出来是 `stacksTo(1)` 的普通物品，
能编译、长得像盔甲、**穿不上**；工具则一律当钻石工具，原 mod 的手感全丢。

所以按名字剥后缀来推：

```
ruby_helmet / ruby_chestplate / ruby_leggings / ruby_boots  →  材质 ruby
ruby_sword / ruby_pickaxe / ruby_axe                        →  材质 ruby
```

这跟绝大多数 mod 的命名习惯对得上，也是我们自己的编辑器里 tier 与 armorMaterial 同名的惯例。
数值按钻石档填默认值，并在警告里点名，让你用之前自己调一遍 —— 不静默糊过去。

名字会发生冲突的地方也处理了：原 mod 完全可能叫 `void_helmet`，剥出来是 `void`，
撞 Java 保留字，条目会被标识符校验直接拒掉。这类名字在真实 mod 里不罕见
（`void` / `air` / `world` / `int` 都有人用），所以分析器会自动改成 `void_mat`，
而不是让你回头一个个手改。

**第三层：代码能力** —— 从 class 文件的常量池推断。这是**证据，不是事实**：

它读每个 class 的常量池，看这个 mod 引用了哪些 API。引用了 `ServerLivingEntityEvents` 就说明它挂了伤害事件，引用了 `AttributeModifier` 就说明它改属性。

每条能力都带「证据」一行，就是命中的那个类名，你可以自己核对。
标「强证据」的是多个线索互相印证，「有证据」是只有单个线索。

还会解析 mixin：`*.mixins.json` 里声明了哪些 mixin 类，这些类的常量池里出现了哪些原版类 ——
按类名相似度排序（`ArrowMixin` 更可能注入 `AbstractArrow` 而不是 `Level`），把最可能的排在前面。

### 关于「提取代码」

**分析器不会把原 mod 的代码抄给你。** 这是刻意的，原因很实在：

反编译出来的方法体依赖它自己的类、自己的工具方法、自己的注册表。
搬到你的工程里，十条有九条编译不过 —— 抄过来的不是能力，是包袱。

所以这块做的是另一件事：**为每种能力准备一份等价实现**。

你在分析报告里勾选「定时任务」，它会附带一段用 `ServerTickEvents` 写的、
只依赖 Fabric API 和原版类的、能直接编译的代码。参数替成你在界面上填的值。

界面上标了 `☑ 勾选 = 附带「XXX」的可编译实现` —— 有这句话的才有现成实现，
标「仅识别」的是我们知道它做了这件事，但没法给你一段等价的通用代码。

内置的效果模板（`core/library/effects.mjs`）：

| 效果 | 干什么 |
|---|---|
| 攻击吸血 | 按造成伤害的比例回血 |
| 概率免伤 | 挨打时按概率免疫 |
| 摔落免疫 | 免疫摔落伤害 |
| 手持时加属性 | 拿着某件物品时获得属性加成 |
| 手持时允许飞行 | 拿着某件物品就能飞 |
| 范围周期效果 | 每隔一段时间给周围玩家回血 |
| 击杀奖励 | 击杀时掉落指定物品 |

这七个模板每一版都会跑一次 `node tests/effects.mjs --build` 真编译验证 ——
模板是给别人直接装进工程用的，编译不过就等于骗人。

#### 发布版 jar 能看到什么、不能看到什么

直接拖进来的第三方 jar 通常只有 `.class`，而且类名被重映射过。分析器读常量池，
所以**看得到**：注册 id、引用了哪些 API、字符串字面量、mixin 配置与候选注入目标、
资源数据文件里的全部内容。**看不到**：方法体怎么写的、原作者的 Java 源码。

界面不会假装能把字节码还原成源码。带签名的发布包会明确提示这一点，
并把「效果模板」指给你 —— 那是可编译的等价实现。

例外是 **sources jar**（里面带 `.java`）：报告会列出源码文件，每个都能点「查看源码」
直接打开正文（纯只读，文本不拼 HTML）。这种包不需要反编译。

当前**没有内置反编译器**。理由是它需要外部 jar 或 JDK 工具链，
会破坏这个工具「零依赖、双击就能跑」的底线，而反编译出来的方法体又搬不进别人的工程
（依赖原 mod 自己的类与注册表）。如果以后要加，入口已经留好：
`core/analyze/classfile.mjs` 解析常量池、`core/analyze/meta.mjs` 判包类型，
加一个「反编译 provider」注册进去即可，不影响现有分析链路。

### 分析器也能加载新工具（扩展系统）

核心分析器只认原版那套（物品 / 方块 / 原版配方 / 材质…）。
但别人的 mod 常有自己的体系 —— Goety 的仪式配方与聚晶、Farmers Delight 的锅与砧板。
把这些硬写进核心，既臃肿，又只对个别包有用。

所以做成了**扩展**：一个文件夹 = 一件新工具，引擎启动时自动扫描装载。

```
core/analyze/ext/<你的扩展>/index.mjs
```

默认导出一个描述对象：

```js
export default {
  id: 'my-ext',
  name: '我的扩展',
  order: 10,
  match: (meta) => meta.id === 'mymod',   // 只对命中的 jar 激活
  contentTypes: {                        // 新增「内容类型」= 拆解台分组
    myConfig: { label: '我的数值', icon: '⚙' },
  },
  fields: {                             // 这些类型在拆解台里可编辑的字段
    myConfig: [{ key: 'value', label: '数值', kind: 'num' }],
  },
  analyze: (ctx) => ({ contents: { myConfig: [...] }, warnings: [] }),
  onExport: (ctx) => ({ files: [], java: [], warnings: [] }),
};
```

`analyze` 负责「读出内容」，`onExport` 是第二层钩子 ——
有些 mod 的数值不在条目里（比如 Forge 配置，改值要落到 toml 或运行时代码才生效），
`onExport` 按「用户改了哪些值」生成对应的产物，同样不用改核心代码。

**核心引擎零改动。** 新增一种 mod 的支持 = 拖一个文件夹进来。

⚠️ **扩展是服务启动时一次性装载的**（刻意对齐 MC 的 mod 语义：改了 mod 要重启游戏）。
新加或改了扩展，**重启 MC Studio 服务**才生效。

目前已装三个：

| 扩展 | 匹配 | 带来什么 |
|---|---|---|
| `goety-base` | modId = `goety` | 112 状态效果 / 125 法术 / 1579 条数值配置 / 18 酿造效果 / 13 附魔 |
| `goety-revelation` | modId = `goety_revelation` | 87 条仪式配方 / 9 个聚晶 / 5 条套装词条 |
| `goety-delight` | modId = `goetydelight` | 18 状态效果 / 5 附魔 / 33 条数值配置 / 111 条仪式料理配方 |

`goety-base` 与 `goety-delight` 的 Forge 配置提取与覆写生成是同一套代码
（`core/analyze/forge/config.mjs` 与 `core/analyze/forge/override.mjs`），
所以两个 mod 的「改数值 → 真回写生效」链路行为完全一致。

## 四、手写一个包

高手可以直接写 JSON 放进 `~/.mcstudio/packs/`，文件名 `<id>.mcpkg.json`：

```json
{
  "format": "mcstudio.pack",
  "formatVersion": 1,
  "id": "my_lifesteal",
  "name": "吸血 20%",
  "kind": "effect",
  "desc": "打中目标回 20% 伤害的血",
  "tags": ["战斗"],
  "origin": { "kind": "manual" },
  "requires": { "platform": ["fabric"], "mcVersion": ["26.3"] },
  "params": [
    { "key": "ratio", "label": "吸血比例", "type": "number", "default": 0.2 }
  ],
  "content": {
    "entries": {},
    "java": [
      {
        "target": "init",
        "name": "吸血",
        "code": "net.fabricmc.fabric.api.entity.event.v1.ServerLivingEntityEvents.AFTER_DAMAGE.register((entity, source, baseDamage, damageTaken, blocked) -> { if (source.getEntity() instanceof net.minecraft.server.level.ServerPlayer attacker) { attacker.heal(damageTaken * {{ratio}}F); } });"
      }
    ],
    "js": [],
    "lang": {},
    "files": [],
    "textures": []
  }
}
```

几个约定：

- `target` 是钩子锚点，可选 `init` / `items` / `blocks` / `tabs`
- Java 代码是**插在方法体里**的，所以不能写 `import` —— 类型一律用全限定名
- `{{key}}` 是参数占位符，`params` 里声明了才会在安装时让你填
- `kind` 可以省略，会按内容自动算（有内容=content，有代码=effect，都有=mixed）

写完点「导入」把它粘进去，或者直接丢进库目录刷新页面。

## 五、几个容易踩的点

**包里的贴图只有「自己画的」会被带走。**
自动改色和矿石合成的贴图不带，是因为它们装到新工程时会按当时的配色重新生成 ——
换个配色主题的工程，带过去的紫色剑反而是错的。

**装包不会覆盖你手改过的生成文件。**
安装只改工程数据（`.studio/project.json`）和钩子，生成要你自己点「生成」。
这样做是为了让「装了什么」和「写了什么」分得开。

**分析别人的 mod 得到的内容，导入时字段会缺。**
方块的硬度、爆炸抗性这类写在代码里的数字，资源文件读不到，会留空用默认值。
装备材质是唯一做了兜底的一档（按套装名推一个、填钻石档数值），因为它缺了就直接坏 ——
盔甲穿不上、工具手感全丢。其余该空的还是空的，报告里不会假装知道。

**26.3 的 ID 化 API 变了，模板里的写法都验过。**
`ItemTags.create()` 没了、`LivingEntity.spawnAtLocation()` 没了、
`BuiltInRegistries.ITEM.get()` 返回 `Optional<Reference<Item>>` 而不是 `Item`。
这些坑都写进了模板注释，以后写自己的效果时可以直接参考。
