# 09 · 扩展与工具包

> 这一篇给「想让 MC Studio 多干点活」的人看。
> 不写代码也能用命令行工具箱；想加新平台、给某个 mod 写友好积木包，照着样板改就行。

引擎里有两种扩展，都**不用改引擎源码**：

| 扩展点 | 解决什么 | 放哪儿 |
|---|---|---|
| 目标适配器 | 支持新的加载器 / MC 版本组合 | `~/.mcstudio/targets/*.mjs` |
| mod 专属积木包 | 给某个 mod 写「积木级」语义，而不是一堆方法调用 | `~/.mcstudio/modpacks/*.mjs` |

放好之后引擎启动时自动扫描，`node studio.mjs blocks targets` / `blocks packs` 里就能看到。

---

## 1. 命令行工具箱

界面里的能力以前只有 HTTP 接口，接不了 CI、写不进脚本。现在都有命令行入口：

```bash
node studio.mjs blocks help                      # 看全部用法
node studio.mjs blocks targets                   # 目标清单（含外部发现的）
node studio.mjs blocks packs --mod examplemod    # 哪些专属包会命中这个 mod
node studio.mjs blocks list --target forge-1.20.1
node studio.mjs blocks compile projects/mymod --target fabric-26.3 --out /tmp/ModLogic.java
node studio.mjs blocks from-jar 某个mod.jar --out 我的库.mcblocks.json
node studio.mjs blocks validate 我的库.mcblocks.json
node studio.mjs blocks install 我的库.mcblocks.json --scope user
node studio.mjs blocks new --name "治疗" --id my.heal --code 'player.heal(%v);' \
  --param v:number --out 我的积木.mcblocks.json
node studio.mjs tools                            # tools/ 里所有脚本的索引
```

也配了 npm 短命令：`npm run blocks -- list`、`npm run tools`。

**所有命令都支持 `--json`**，输出结构化结果，不掺人话；退出码 `0` = 成功、非 `0` = 有问题。拿它接 CI 很直接：

```bash
# 分享前先体检，坏库直接让流水线挂掉
node studio.mjs blocks validate dist/*.mcblocks.json || exit 1

# 把工程里的积木程序编成 Java，塞进后续步骤
node studio.mjs blocks compile projects/mymod --json > /tmp/visual.json
```

`blocks compile` 读的是工程 `.studio/project.json` 里存的 `visual.programs` —— 也就是**界面上搭好并保存的那份**。命令行和界面走同一条编译路径，不存在「界面能编、命令行编出来不一样」。

## 2. 加一个新目标（加载器 + MC 版本）

### 契约

一个 `.mjs` 文件，`export default` 一个对象：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✓ | 唯一，如 `neoforge-1.21.1` |
| `label` | ✓ | 界面显示名 |
| `platform` | ✓ | `fabric` / `forge` / `neoforge` / `paper` … |
| `mcVersion` | ✓ | 如 `1.21.1` |
| `javaVersion` | | 目标 JDK |
| `defaults` | | 新建工程时用的默认版本号（loom / loader / gradle…） |
| `features` | | 能力开关，模块据此决定生成策略 |
| `scaffold(ctx)` | | 生成工程骨架，返回 `[{path, content}]` |
| `java` | | 代码生成辅助 |
| `apiJar` | | 「实测法」识别 mod 目标用的 MC jar 路径，字符串或 `({home}) => 路径` |
| `signatureKey` | | 事件签名用哪套（`forge` / `fabric26`）；不给就按 `platform` 推 |

完整接口说明在 `core/target/registry.mjs` 文件头，实现照着
`core/target/fabric-26.3/adapter.mjs` 抄最快。

### 放哪里

三选一，按优先级：

1. `MCSTUDIO_TARGETS=<目录>` 环境变量 —— CI 或多版本切换，多个目录用系统路径分隔符隔开
2. `~/.mcstudio/targets/` —— 装一次，所有工程都能用
3. 代码里调 `registerTarget(adapter)` —— 插件式集成

引擎启动时自动扫描；`blocks targets` 会把外部目标标成「外部」并列出加载诊断。
同一个 id 想覆盖内置目标，设 `MCSTUDIO_TARGETS_OVERWRITE=1`。

### 两件容易漏的事

- **事件签名**：编译器按适配器的 `platform`（或显式 `signatureKey`）挑事件方法参数，
  不再靠目标 id 的字符串前缀猜。新平台要确认 `SIGNATURES` 里那套参数对得上。
- **积木模板**：内置积木的 `java` 是按目标 id 分派的（`'fabric-26.3': …`）。
  新目标要么给积木补模板，要么让自定义积木用全目标（见第 4 节）。
  `blocks validate` 的覆盖率矩阵会告诉你「这个目标下有几条积木能用」。

> 可照抄的样板：`examples/extend/targets/fabric-demo.mjs`

## 3. 给某个 mod 写专属积木包

通用扫描（`modlib.mjs`）扫的是 `public static` 方法，产出
「调用 `WandUtil.chainLightning(a,b,c,d)`」这种零件 —— 对会写代码的人有用，对小朋友没用。
专属包写的是**积木级语义**：「给玩家一个聚晶」「把灵魂能量设成 500」。

### 契约

一个 `.mjs` 文件，导出 `pack`：

```js
export const pack = {
  id: 'mymod',                    // 唯一
  label: '我的 mod · 专属积木',    // 生成日志里显示
  modIds: ['mymod'],              // 按 mod id / namespace 命中（小写）
  // match(report) { ... },      // 可选：复杂判断；给了它就不看 modIds
  build({ targetId, report, opts }) {
    return {
      blocks: [ /* 积木定义，格式跟 .mcblocks.json 里一样 */ ],
      categories: [ /* { id, label, icon, color } —— 不写界面就显示内部 id */ ],
      notes: [ /* 生成日志 */ ],
    };
  },
};
```

### 放哪里

1. `~/.mcstudio/modpacks/*.mjs` —— 全局
2. `MCSTUDIO_MODPACKS=<目录>` —— CI
3. `<工程>/.studio/modpacks/*.mjs` —— 只在这个工程生效

内置包在 `core/visual/modpacks/`（Goety 那份是完整范例）。
**外部包 id 与内置相同时外部优先** —— 可以拿它修内置包的 bug，不用等引擎发版。

### 两条保险

- **隔离**：一个包语法错或 `build()` 抛异常，只跳过它，其它包和通用扫描照常出结果，
  问题记进 `blocks packs` 的诊断里，不会静默吞掉。
- **不串台**：`match()` / `modIds` 决定命中，不相干的 mod 不会拿到别的包的积木。

> 可照抄的样板：`examples/extend/modpacks/demo.mjs`

## 4. 自定义积木：默认全目标可用

「用代码造一条积木」和 `blocks new` 造出来的积木，**默认在所有已登记目标下都能用**
（包括你后来加的外部目标）。

以前默认只挂 `fabric-26.3`，换到 Forge 工程积木就从库里消失了 —— 这已修掉。
`userDef.targets` 记着它适用哪些目标，`userDef.targetId` 保留着兼容旧库文件。

真要写平台专属代码，就显式收窄：

```bash
# 只在 Forge 下可用
node studio.mjs blocks new --target forge-1.20.1 --name ... --id ... --code ...
# 界面：取消勾选「所有目标都能用」
```

## 5. 分享前体检：`blocks validate`

装库时只检查「有没有 id / shape / java」，太浅了。体检器查的是**会不会生成坏代码**：

| 级别 | 检查项 |
|---|---|
| ERROR | 模板里的 `%foo` 没有对应参数声明（生成的 Java 会残留 `%foo`） |
| ERROR | 声明了 `bodySlots` 却没有 `%body` / `%elseBody`（凹槽里的积木会悄悄丢失） |
| ERROR | 重复 id、id / shape / 参数名不合法、空模板 |
| WARN | 参数声明了没用到、分类没登记（界面显示内部 id）、各目标模板参数不一致 |
| WARN | 某个目标下 0 条积木可用、目标 id 不认识、库版本不匹配 |

输出带**目标覆盖矩阵**，一眼看出这个库在 Fabric / Forge 下各有多少积木能用：

```
my-lib.mcblocks.json  ✓ 通过  32 条积木 / 1 个目标
   fabric-26.3          0/32 可用  0%
   forge-1.20.1        32/32 可用  100%
   warn    这个库在目标 fabric-26.3 下没有任何可用积木（0/32）
```

Goety 那三个库就是这样 —— 它们本来只支持 Forge，0% 不是错，但分享给别人之前该说清楚。

`blocks from-jar` 生成完会顺手体检一次，有问题直接列出来。

## 6. 常见问题

**放了新的 adapter / pack，界面没变化？**
引擎是启动时扫描的，重启服务。`blocks targets` / `blocks packs` 能立刻确认有没有扫到，
诊断区会写明是哪个文件加载失败。

**外部包写崩了会不会把整个生成搞挂？**
不会。看 `blocks packs` 的「诊断」段。

**`blocks compile` 说「工程里还没有积木程序」？**
界面上搭完要点「保存」写进 `.studio/project.json`；或者用 `--root` 指向对的工程。

**`--out` 写到别处去了？**
相对路径按当前工作目录解析，建议给绝对路径。

**想在 CI 里跑全量回归？**
`node tests/extensible.mjs` 专门测这两个扩展点、体检器和所有 CLI 子命令，
夹具就是 `examples/extend/` 里的样板，跟用户照抄的是同一份文件。
